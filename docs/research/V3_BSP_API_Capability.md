# V3 — BSP API Capability Audit: Can a Third Party Actually Get the Data?

Research date: 2026-09-05. Method: public developer documentation only (no accounts created, no dashboards logged into). Every claim below is tagged with a source link. Where a page required login to reveal a full response schema, or where a docs site is a JS-rendered SPA that would not yield field-level text to a fetch, this is flagged explicitly rather than guessed.

**Important correction to the brief:** Meta's own field is called `health_status` (not `messaging_health_status`), and the phone-number quality field is `quality_rating` — confirmed directly against Meta's docs (cited below). The messaging-tier field `messaging_limit_tier` is **deprecated**; the current field is `whatsapp_business_manager_messaging_limit`.

**Important note on scope:** "WATI" and "Wati.io" in the brief are the same company/product (docs at `docs.wati.io`, product at `wati.io`). They are covered as one row, not duplicated with invented differences.

## Legend

- **Yes** — documented, with a live docs URL, at the field/endpoint level.
- **Partial** — an endpoint exists but either (a) only covers part of the ask, or (b) I could not confirm the exact field(s) from a publicly reachable page (login-gated sample, JS-rendered SPA, etc.) — noted per cell.
- **No** — the capability is documented as absent, deprecated, or dashboard-only (i.e., actively confirmed not to be an API).
- **Not documented** — I could not find public documentation either way. This is not the same as "No." (Per instruction: this is the more honest answer when evidence is simply absent.)

## Provider-by-provider detail, with sources

### Meta WhatsApp Cloud API (direct)

1. **Quality rating — Yes.** `GET /{PHONE_NUMBER_ID}?fields=quality_rating` returns `GREEN`/`YELLOW`/`RED`/`NA`/`UNKNOWN`; also returned in the `/{WABA_ID}/phone_numbers` list. [Business phone numbers doc](https://developers.facebook.com/documentation/business-messaging/whatsapp/business-phone-numbers/phone-numbers). Related but distinct: `health_status` field (not "messaging_health_status") returns a `can_send_message` value (`AVAILABLE`/`LIMITED`) per node (phone, WABA, business, app). [Messaging and Calling Health Status](https://developers.facebook.com/documentation/business-messaging/whatsapp/support/health-status/).
2. **Messaging tier — Yes.** `GET /{PHONE_NUMBER_ID}?fields=whatsapp_business_manager_messaging_limit` returns e.g. `TIER_250`. The old `messaging_limit_tier` field is **deprecated**. Limits are now shared across all numbers in a Business Portfolio (changed Oct 2025). [Messaging Limits doc](https://developers.facebook.com/docs/whatsapp/messaging-limits/).
3. **Templates — Yes.** `message_templates` endpoint; status values include `APPROVED`/`REJECTED`/`PAUSED`/`DISABLED`/`Active – Quality pending/High/Medium/Low`; category is `AUTHENTICATION`/`MARKETING`/`UTILITY`; rejection detail surfaces via the `message_template_status_update` webhook with a `rejected_reason` (e.g. `INCORRECT_CATEGORY`, `TAG_CONTENT_MISMATCH`). [Template fundamentals](https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/overview).
4. **Send history — No.** There is no Graph API endpoint to retrieve previously sent or received messages. The Cloud API is push-only: you receive `messages`/`statuses` webhooks in real time and must persist them yourself. Confirmed by absence across Meta's own docs and multiple third-party integration guides that all describe "store what arrives via webhook" as the only pattern.
5. **Opt-in/opt-out — Not documented at a queryable per-contact level.** Meta requires businesses to obtain and manage consent themselves; there is no `opt_in_status` field on a contact. A user-facing "Offers and announcements" toggle (lets a WhatsApp user disable marketing templates from a specific business) is described in secondary sources alongside a marketing-subscription webhook event, but I could not confirm this against a primary Meta docs page in this session — **flagged in Could-Not-Establish below**.
6. **Webhooks — Partial.** The `messages` (status) webhook fires `sent`/`delivered`/`read`/`failed`/`played`, with `failed` including an error code/title (e.g. `131049`, "not delivered to maintain healthy ecosystem engagement" — a pacing/quality throttle, not a block). [Status messages webhook reference](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/reference/messages/status). Account-level signals exist via `account_update` (`ACCOUNT_RESTRICTION`, `ACCOUNT_VIOLATION`, `DISABLED_UPDATE`, `PARTNER_ADDED/REMOVED`, etc.) — [account_update webhook reference](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/reference/account_update) — but **no event value in either webhook means "this user blocked or reported you."** The closest available proxies are quality-rating decay and pacing-related `failed` errors, both aggregate/delayed, not identifying a specific blocking user.
7. **Auth model & access — Yes, open at the API layer.** No paid "tier" gates raw Graph API access itself (Meta monetizes per conversation, not per API seat). Rate limits reported in secondary/community sources (not an official page fetched directly in this session): up to 80 messages/second per number (upgradeable to 1,000 MPS), ~10 requests/second at the endpoint level.
8. **Third-party integration on behalf of a customer — Yes, formal program.** Meta has an explicit Tech Provider / Solution Partner model: Tech Providers ship software with clients paying Meta directly; Solution Partners get a Meta credit line and bill clients themselves. Requires App Review approval for **Advanced Access** to `whatsapp_business_management` (read client account data) and `whatsapp_business_messaging` (send on their behalf), and onboarding is done via **Embedded Signup** (an OAuth-style flow where the client authorizes sharing specific WABA/number assets without handing over their own Meta login). [Become a Tech Provider](https://developers.facebook.com/documentation/business-messaging/whatsapp/solution-providers/get-started-for-tech-providers), [Embedded Signup overview](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/overview/).

### Gupshup

1–2. **Quality rating & messaging tier — Yes, one endpoint.** `GET https://partner.gupshup.io/partner/app/{appId}/ratings` returns `phoneQuality` (`GREEN`/`YELLOW`/`RED`) plus `oldLimit`/`currentLimit` (`TIER_10K` etc.) and an `event`/`eventTime`. Docs explicitly note this is intended for **once every 24 hours** (hard rate cap is 10 requests/minute → 429). [Get Quality Rating](https://partner-docs.gupshup.io/reference/get_partner-app-appid-ratings). A separate `GET /partner/app/{appId}/health` checks connectivity/config health (not quality). [Check Health](https://partner-docs.gupshup.io/reference/get_partner-app-appid-health).
3. **Templates — Yes.** Dedicated "Get Templates" and "Template Analytics" partner endpoints, plus a sync-from-Meta endpoint. [Template Management section, partner-docs.gupshup.io](https://partner-docs.gupshup.io/reference/get_partner-app-appid-templates); approval/status semantics: [Template Message Approvals & Statuses](https://docs.gupshup.io/docs/message-template-approvals-statuses).
4. **Send history — No.** No documented "get past messages" endpoint; only real-time webhook events (`enqueued`/`failed`/`sent`/`delivered`/`read`) were found. [Template messages doc](https://docs.gupshup.io/docs/template-messages).
5. **Opt-in/opt-out — No, going forward.** Gupshup had legacy Opt-in/Opt-out and Block-User APIs, but per Gupshup's own support article these (and their UI) were **deprecated by 30 June 2025**, and any app created after 1 Aug 2025 does not support them at all. [Prepare for Sunset of Optin Optout service](https://support.gupshup.io/hc/en-us/articles/35183519921689-Prepare-for-Sunset-of-Optin-Optout-service-by-Gupshup-before-31st-Aug-2024).
6. **Webhooks — Partial.** Enqueued/failed/sent/delivered/read confirmed. A "Block Users" / "Get Blocked Users list" partner API exists, but this is for **the business blocking a user** (moderation), not for detecting that a user has blocked the business — it does not answer the block/report question the brief is asking about.
7. **Auth/access — Yes, self-serve**, with explicit rate limits on partner endpoints as above.
8. **Third-party on behalf of customer — Yes, full Partner Portal.** Partners manage client apps under a `PARTNER_APP_TOKEN`, and an "OBO to Embed flow" (Own-Business-Onboarding to Embedded Signup) lets a partner attach to a client's WABA/credit line without the client handing over their own Meta credentials. [Partner Portal Onboarding APIs](https://partner-docs.gupshup.io/reference/app-onboarding-apis).

### WATI (docs.wati.io — same product as "Wati.io")

1. **Quality rating — Partial/Yes via webhook.** A dedicated "Phone Number Quality Update Event" webhook exists in WATI's webhook catalog, confirming Meta's quality signal is passed through in real time. [Webhook Events & Payloads index](https://docs.wati.io/reference/message-received) (see sidebar: Phone Number Quality Update Event, Template quality update, WABA Status Review Update). A "Get phone number detail" GET endpoint also exists (`/api/v2/whatsapp/{wabaId}/{phoneNumber}/profile`) but its response schema is login-gated in the docs UI, so I could not independently confirm `quality_rating` appears in that JSON body. [Get phone number detail](https://docs.wati.io/reference/get_api-v2-whatsapp-wabaid-phonenumber-profile).
2. **Messaging tier — Partial.** WATI's help center documents phone-number *status* states — Connected, Flagged (quality dropped, tier-upgrade blocked), Offline, Restricted (limit hit), Banned — but I found no explicit numeric-tier field returned by a GET endpoint. [Understanding your WhatsApp phone number connection status](https://support.wati.io/en/articles/11463154-understanding-your-whatsapp-phone-number-connection-status).
3. **Templates — Yes.** `GET /api/ext/v3/messagetemplates` (and legacy v1/v2 equivalents), plus three dedicated webhooks: Template Status Update, Template quality update, Template category update. [MessageTemplate API index](https://docs.wati.io/reference/get_api-ext-v3-messagetemplates-template-id); [Template Status Update webhook](https://docs.wati.io/reference/template-status-update).
4. **Send history — Yes, the strongest finding in this audit.** `GET /api/ext/v3/conversations/{target}/messages` — `target` can be a phone number, conversation ID, contact ID, or channel-scoped variant; paginated (`page_number`, `page_size` max 100). Confirmed available on the entry-level **Growth** plan (not enterprise-gated). [Get messages](https://docs.wati.io/reference/get_api-ext-v3-conversations-target-messages); [Endpoint availability by plan](https://docs.wati.io/reference/endpoint-availability-by-plan) (shows `/getMessages` ✅ on Growth/Pro/Business). No documented maximum lookback window was found — **flagged below**.
5. **Opt-in/opt-out — Not documented.** No explicit opt-in field found in the reachable Contact API schema; there is a GDPR-flavored "soft-delete a contact" endpoint, but that is deletion, not consent state.
6. **Webhooks — Yes, richest catalog found across all eight providers.** Message Received, New Contact Message, Session/Template Message Sent, Delivered, Read, Replied, Failed, Template Status/Quality/Category Update, WABA Status Review Update, Phone Number Quality Update, WABA Account Deleted/Content Updated, Phone Number Deleted, Call Status, CTA URL Clicked, Chatbot Triggered — plus BSUID variants of most. [Webhook index](https://docs.wati.io/reference/introduction-1). **No block/report event exists in this list.**
7. **Auth/access — Yes, explicitly documented per-endpoint by plan.** `/getMessages`, `/getMessageTemplates`, `/getContacts`, `/sendTemplateMessage` etc. are all available starting on the Growth plan; team-assignment, chatbots, and custom segments require Pro/Business. [Endpoint availability by plan](https://docs.wati.io/reference/endpoint-availability-by-plan).
8. **Third-party on behalf of customer — Partial.** The documented model is a per-account API key/token generated inside the customer's own WATI account for a developer to use; no OAuth/partner-marketplace program comparable to Meta's or Gupshup's was found in the public docs.

### AiSensy

Public documentation is thin relative to the others, and AiSensy's fuller "Project API"/"Direct API" reference lives on Stoplight, which renders via JavaScript — fetches in this session returned only navigation shells, not field-level content, for those pages. What is confirmed:
- A campaign-send API (`POST https://backend.aisensy.com/campaign/t1/api/v2`) requiring `apiKey`, a pre-approved `campaignName`/template, `destination`, and optional `tags`/`attributes`. [API Reference Docs](https://wiki.aisensy.com/en/articles/11501889-api-reference-docs).
- "Project Webhook" / "Direct Webhooks" exist and are HMAC-signed (`X-AiSensy-Signature`), described in AiSensy's own webhook guide. [Direct Webhooks](https://aisensy.stoplight.io/docs/direct-api/65e6db1a11997-direct-webhooks) (page shell only; content not independently verified).
- Quality rating, messaging tier, a template list/status/rejection-reason endpoint, per-contact message history, and a formal opt-in field are all **not documented** in any publicly reachable page found in this session. This is an absence-of-evidence finding, not a confirmed "No" — **flagged below** as an area needing an authenticated look at the Stoplight docs.

### Interakt

- Webhooks are the one clearly and publicly documented capability: subscribe to receive `Sent`/`Delivered`/`Read`/`Failed` status for template messages, plus a separate webhook for inbound customer messages — **but gated to the Growth or Advanced plan** (not Starter). [Interakt APIs and Webhooks overview](https://www.interakt.shop/resource-center/interakt-apis-and-webhooks-an-overview/); [webhook detail](https://www.interakt.shop/resource-center/interakts-webhooks-for-customer-messages-sent-template-status/).
- Explicit, unusually clear plan-gating: **"Public APIs are not accessible on Starter Plan."** Growth = 300 requests/minute, Advanced = 600/minute, Enterprise = configurable to Meta's allowed rate. [Same overview page].
- A Template Send API and a "Get Users API" (contact records, filterable by created/modified date) exist, but neither is a template-status/rejection-reason list nor a message-content history endpoint.
- Quality rating, messaging tier, per-contact message history, opt-in/opt-out state, and a block/report signal are all **not documented** in the pages reachable in this session.

### Zoko

- Confirmed endpoints: `GET /account/templates` (template list — [Get Message Templates](https://developers.zoko.io/reference/get_account-templates-1)); `GET /customer` and `GET /customer/{id}` (customer list/detail, [Get Customer List](https://developers.zoko.io/reference/get_customer-1)); `PUT /customer/{id}/tags` (bulk tag update); a webhook Register/List/Update/Delete API ([Webhook API](https://docs.zoko.io/messaging-api/webhook-api/)).
- **Opt-out is modeled as a tag, not a formal field:** when a customer clicks an opt-out link in a template, Zoko auto-applies a system tag `OPT_OUT` to that customer's profile, which is then readable via the Customer API's tags. [Setting up Templates with OPT-OUT Options](https://www.zoko.io/learning-article/templates-with-opt-out-options). No equivalent "opted-in" flag was found.
- Quality rating and messaging tier are described only as a dashboard experience in Zoko's learning-center articles (e.g. "How to Get Your Tiers Upgraded," "Understanding Quality Ratings") — **no API field or endpoint was found**, which is a confirmed "No" for API access, not merely an absence of evidence.
- A "Delete Messages of a Customer" operation exists on the Customer API (implying Zoko stores per-customer message history server-side), but no corresponding public **Get** endpoint for that history was found — flagged below as worth a second, authenticated look.

### DoubleTick

- **Send history is clearly and fully documented** — `GET https://public.doubletick.io/chat-messages?wabaNumber=...&customerNumber=...&startDate=DD-MM-YYYY&endDate=DD-MM-YYYY` returns a full per-message JSON array with `messageTime` (epoch ms), `messageOriginType` (`CUSTOMER`/`USER`/`SYSTEM`), delivery/read/error counts, and template linkage. A separate "Export Chats" endpoint also exists. [Get chat messages for a customer of WABA number](https://docs.doubletick.io/docs/get-chat-messages-1). No maximum lookback window is documented — flagged below.
- Templates: `Get WhatsApp Templates` plus Create/Edit/Delete exist ([docs index](https://docs.doubletick.io/docs/getting-started)); category rules are documented separately ([Template Categories in WhatsApp API](https://learn.doubletick.io/templates/template-categories-in-whatsapp-api)), but I could not independently confirm a rejection-reason field in the GET response.
- **Quality rating and messaging tier are explicitly dashboard-only.** DoubleTick's own help docs describe an "Account Quality" box on their dashboard Home page (High/Medium/Low) and prose-only status states (Flagged/Connected) — there is no corresponding entry in the API reference sidebar (which lists Outgoing Messages, Chat Messages, Broadcasts, Templates, Customer, Team Member, Wallet, Webhook — no Quality/Health/Account section). [How to check account quality](https://learn.doubletick.io/meta-business-setup/account-quality/how-to-check-account-quality); [API docs index](https://docs.doubletick.io/docs/getting-started). This is a confirmed "No" for API access.
- Auth is a simple API key (`Authorization: key_xxx`), self-serve via account Settings. No OAuth/partner program for third parties was found; the "Custom CRM Integration" and iframe-embed docs are for a single account owner integrating their own systems, not for a third party managing many DoubleTick customers' WABAs.

## What an integrated product could and could not see

**The decision-relevant answer, stated plainly:** per-contact send history and quality rating can both be obtained — but from **different places, and not from the same easy path for every customer.**

- **Quality rating and messaging tier are properties of the WABA/phone number inside Meta's own system, not properties of the BSP layered on top of it.** Meta's Graph API exposes both directly (`quality_rating`, `whatsapp_business_manager_messaging_limit`) to *any* app the WABA owner grants access to — via Business Manager asset-sharing, or formally via the Tech Provider/Solution Partner + Embedded Signup program — **independent of which BSP the customer uses to actually send messages.** This is an inference from combining verified individual facts (the field exists on the phone-number object; Solution Partner access to a shared WABA is a documented, separate grant from who sends messages), not a single page that states it outright — flagged as such. Practically: a third-party product does not strictly need Gupshup's, WATI's, or anyone else's cooperation to read quality rating and tier, *if* it can get the end customer to grant it partner/System-User access to their WABA in Meta Business Manager. Two BSPs (Gupshup, and WATI via webhook) also pass this through their own APIs, which is a convenience but not the only path.
- **Per-contact send history with timestamps is the opposite story: it is BSP-specific, and roughly half the reviewed BSPs do not expose it at all.** Meta's raw Cloud API has **no** history endpoint — a product built directly on Meta must start capturing its own log from day one via webhooks, with zero backfill of anything sent before integration. Among the BSPs, **WATI** and **DoubleTick** have clean, documented, paginated/date-ranged history endpoints. **Gupshup has none** (webhooks only). **AiSensy, Interakt, and Zoko have no publicly documented history endpoint either** (Zoko's "Delete Messages of a Customer" operation hints storage exists, but no public Get was found). This means: a frequency-rule engine that depends on "how many messages has this contact received in the last N days" is **only turnkey-buildable today for customers on WATI or DoubleTick** among the providers reviewed. For every other provider (including raw Meta), the product must become the system of record itself, capturing every send/status event from its own install date forward — which is workable, but means day-one accuracy is zero and improves only as the integration accumulates its own history.
- **A "user blocked or reported you" signal does not exist, anywhere, from any provider reviewed.** The Meta status-webhook enum is `sent`/`delivered`/`read`/`failed`/`played` — no block/report value. The best available proxies are indirect and delayed: phone-level `quality_rating` decay over a rolling 7-day window, template-level quality decay, and `failed`-status webhooks carrying pacing/quality error codes (e.g. `131049`). None of these identify which specific contact blocked or reported the business, only that aggregate sentiment has soured. Gupshup's "blocked users" API is the business blocking users, the reverse of what's needed.
- **Opt-in/opt-out as a portable, provider-verified field essentially does not exist.** Meta leaves consent record-keeping to the business; Gupshup's legacy opt-in/opt-out API is being sunset; Zoko approximates it with a mutable `OPT_OUT` tag; nobody else documents it. A compliance-oriented product cannot pull "ground truth" consent from any provider's API — it has to be the source of truth for consent itself, informed by webhook-observed behavior (e.g., a user replying "STOP") rather than a queryable status field.
- **Templates (status/category/rejection reason) and delivery-status webhooks (sent/delivered/read/failed) are close to universal** — Meta, Gupshup, WATI, and DoubleTick all have clearly documented endpoints/webhooks for these; AiSensy, Interakt, and Zoko have partial or unconfirmed template-list documentation but at minimum support sending pre-approved templates and receiving delivery-status webhooks. This part of an integrated product is safely buildable across the board.
- **Access model:** getting API access at all is not gated to enterprise plans anywhere reviewed **except Interakt**, which explicitly locks Public API and webhook access out of its Starter plan. WATI documents entry-plan (Growth) access to essentially the full v3 API including message history. Everyone else's docs are silent on plan-gating (an absence-of-evidence gap, not a confirmed "open to everyone").
- **On-behalf-of-customer integration:** only Meta (Tech Provider/Solution Partner + Embedded Signup) and Gupshup (Partner Portal + OBO-to-Embed) have a real OAuth-like partner model documented. Every other BSP reviewed (WATI, AiSensy, Interakt, Zoko, DoubleTick) documents only a plain API-key model — meaning, per the publicly available docs, the end customer would need to generate and hand over their own API key to a third-party product for those five providers, rather than approving a scoped, revocable grant.

2. **Whether Meta's "Offers and announcements" user-facing marketing opt-out surfaces via a documented webhook** (secondary sources named a `MARKETING_SUBSCRIPTION_UPDATE`-style event; I could not confirm this against a fetched Meta primary-source page).
3. **AiSensy's full Stoplight "Project API"/"Direct API" reference content** — quality rating, messaging tier, template list/rejection-reason, and message-history endpoints may or may not exist behind that JS-rendered documentation; the section headings visible via search (Business, Project, Messages, Contact, Campaign, Catalogue, Media, Webhook) suggest more may be documented than I could verify field-by-field.
4. **Interakt's full API reference / Postman collection** beyond the public overview article — template list detail, and any additional endpoints not mentioned in the overview page.
5. **Zoko's full Message API and Customer API response schemas** — the ReadMe/ Stoplight-style reference pages returned mostly navigational shells rather than field-level JSON on the fetches attempted; in particular, whether a "Get Messages for a Customer" endpoint exists alongside the confirmed "Delete Messages of a Customer" operation.
6. **DoubleTick's exact template GET response schema** (to confirm a rejection-reason field) and its webhook event enum (sent/delivered/read/failed vs. something else).
