# R5 — Competitor Design Inspiration for Pre-Send Campaign Operations

**Purpose:** product-design inspiration for a pre-send "campaign operations" pipeline (ingest audience+message → resolve identities → check against rules → human decides → seal immutable evidence record → hand off to send tool) for regulated lenders in India. This is NOT a market-sizing or vendor-selection document — it is a pattern library for our own IA/workflow/API/packaging decisions.

**Method:** desk research only (public docs, product pages, help centers, pricing pages, API references) via ~27 web searches/fetches on 2026-09-11. No live product trials, no screenshots captured directly (cited from official marketing/docs pages). Everything below is labeled **[fact]** (directly stated by a primary source, cited) or **[inference]** (my synthesis/read of gaps between sources). Where a vendor's site was marketing copy rather than documentation, that is noted — treat pricing and workflow-state claims accordingly.

---

## 1. Veeva Vault PromoMats

**Sources:** [Veeva PromoMats – MLR Review](https://www.veeva.com/products/veeva-promomats/mlr-review/), [Veeva PromoMats Datasheet](https://www.veeva.com/wp-content/uploads/2014/05/Veeva-Vault-PromoMats-Datasheet.pdf), [PromoMats Overview – Veeva Vault Help](https://commercial.veevavault.help/en/gr/7479/), [Veeva Vault Developer Portal API Reference](https://developer.veevavault.com/api/26.1/), [How to Access the Audit Trail of a Document in Vault](https://support.veeva.com/hc/en-us/articles/360003913933-How-to-Access-the-Audit-Trail-of-a-Document-in-Vault-PromoMats-and-Vault-Medical)

**(a) Check result / report presentation** — [fact] PromoMats centers on **document-level annotations and redlines** rather than a single pass/fail score: reviewers leave inline "Linked Reference Annotations" tying a specific claim/sentence to a specific source document, and these are automatically "harvested" into claim records in a **Claims Library** [fact, Veeva PromoMats Datasheet / MLR Review page]. Severity vocabulary is workflow-state-based (document lifecycle states), not a risk score — the "finding" *is* the annotation thread on the passage itself. [inference] This is a fundamentally different mental model from a scored checklist: the evidence of "why" is the citation link itself (claim → reference document → page/paragraph anchor), which is unusually rigorous and directly reusable as legal evidence. "Auto-Update Reference Anchors" keeps those citations valid when the underlying reference document is revised [fact, Veeva PromoMats 2025 Innovation Guide]. There is no visible pattern for surfacing "what was NOT checked" in public materials [inference — likely because MLR review is document-complete by design: nothing ships without full annotation coverage].

**(b) Workflow & roles** — [fact] Configurable, tiered review workflows: "Tier-Based Review — a variable approach informed by content reuse, reducing average time to approval by 50–75%" [Veeva PromoMats MLR Review page]. Multi-document and multi-team workflows let Medical, Legal, and Regulatory reviewers work in parallel on the same asset with role-scoped visibility [fact, Datasheet]. E-signatures and configurable approval states provide non-repudiation [fact]. Audit trail captures every action performed on the document — access via a dedicated "Audit Trail" tab on the document record [fact, Veeva Support article].

**(c) Information architecture** — [fact] The **primary object is the document/asset** (a piece of promotional content), not the campaign — PromoMats is a content-management application first. Claims and references are secondary linked objects hung off the asset. Digital Asset Management, Content Strategy, and "Commercial Content Kernel" are separate top-level modules in the product nav [fact, veeva.com/products/veeva-promomats/].

**(d) API design** — [fact] Built on the general-purpose **Vault Platform REST API** (documents, objects, workflows are generic Vault resources, not PromoMats-specific endpoints) — see [developer.veevavault.com/api/26.1](https://developer.veevavault.com/api/26.1/). [inference] This "generic object + generic workflow engine, specialized by configuration" approach is a mature enterprise-CMS pattern; it costs Veeva a steeper initial API learning curve but buys huge configurability. No public webhook/idempotency documentation was found in this pass.

**(e) Packaging & pricing** — [fact] No public pricing; contact-sales only, confirmed via [Capterra](https://www.capterra.com/p/173465/Veeva-Vault/) and [Software Advice](https://www.softwareadvice.com/cms/veeva-vault-profile/) — typical of enterprise CLM/regulated-content suites. Priced per-seat/per-module in practice per third-party reviews [inference, unverified primary].

**(f) Steal / avoid** — **Steal:** the claim-to-source citation object as a first-class, reusable, auto-maintained record (Claims Library) — this is the single best pattern for "how do you show why" in a regulated-check product. **Avoid:** the document being the unit of work rather than the campaign/send — for a high-volume, high-frequency lending campaign operation, a document-centric IA would be too slow; we need the *campaign/send* as the primary object with checks and evidence hanging off it, not the reverse.

## 2. Saifr (Fidelity Labs)

**Sources:** [SaifrReview product page](https://saifr.ai/saifrreview), [Saifr FAQs](https://saifr.ai/faqs), [Saifr About](https://saifr.ai/about), [Fidelity Investments RegTech launch release](https://newsroom.fidelity.com/pressreleases/fidelity-investments--launches-innovative-new-regulatory-technology--regtech--business-to-help-finan/s/b776e743-d2cc-4f46-a730-1ae9cb5d2e07)

**(a) Check result presentation** — [fact] Saifr's stated finding format is explicit and reusable for us verbatim: **"Highlight potential compliance risks → Explain why content was flagged → Suggest more compliant phrasing → Recommend potential disclosures."** [saifr.ai/saifrreview] That is a four-step finding anatomy: *what/why/fix/require*. Findings are categorized by regulation-linked type (e.g., "promissory, misleading, exaggerated, or unwarranted" language; "comparison, ranking, and rating claims"; "investment performance claims"; "testimonials"; "tax-free/tax-exempt income references") mapped explicitly to **FINRA 2210, SEC 482, SEC Modernized Marketing Rule** [fact]. It also surfaces non-compliance-risk quality scores ("sentiment," "readability level") alongside compliance flags — i.e., it blends compliance and content-quality signals in one panel [fact]. Language throughout is hedged ("potential risks," "leads for further investigation") — Saifr explicitly disclaims it does not replace human legal/compliance judgment [fact, saifr.ai footer disclaimer]. No public description found of how it shows what was NOT checked.

**(b) Workflow & roles** — [fact] Four access surfaces to the same underlying AI: **(1) Workflow** — centralized real-time collaborative review where "stakeholders can comment and edit"; **(2) Add-ins** — scans inline inside the authoring tool (Word/Outlook/Adobe/Superhuman, per partnerships); **(3) Document submission** — content contributors get visibility into findings without needing the full tool; **(4) API** — embed the scan into your own pipeline [fact, saifr.ai/saifrreview]. [inference] The "four surfaces, one engine" packaging is a strong pattern for meeting reviewers/creators/compliance officers where they already work, rather than forcing everyone into one UI.

**(c) Information architecture** — [inference from product page] The primary object appears to be the **content draft/document**, with the compliance officer and the marketer sharing the same view of the flagged draft (collaboration-first, not queue-first).

**(d) API design** — [fact] "Build compliance risk scanning into your processes and tools" via API is listed as a first-class access mode, but no endpoint-level documentation was surfaced publicly in this pass — API details appear to be gated behind sales/partner access (Microsoft Azure AI model catalog, ServiceNow, Adobe, Superhuman partnerships are the discoverable integration surface) [fact, saifr.ai/microsoft-azure].

**(e) Packaging & pricing** — [fact] "License pricing available per user or enterprise. For more info, please contact Sales." — no self-serve pricing [saifr.ai/saifrreview].

**(f) Steal / avoid** — **Steal:** the four-part finding anatomy (flag → explain why → suggest fix → recommend required disclosure) — this maps almost directly onto our "fix / accept-with-reason / abandon" decision model and should structure our finding schema. **Avoid:** Saifr's public materials give no visible language for uncertainty/coverage limits beyond a boilerplate legal disclaimer — that's a missed design opportunity for building trust; we should be explicit and specific (not just legalistic) about what a check did *not* look at.

## 3. Luthor (YC)

**Sources:** [Luthor homepage](https://www.luthor.ai/), [YC launch](https://www.ycombinator.com/launches/QSd-luthor-ai-compliance-infrastructure-for-regulated-marketing), [YC company page](https://www.ycombinator.com/companies/luthor)

**(a) Check result presentation** — [fact] Luthor's homepage shows a concrete UI pattern worth copying almost exactly: each finding is a card with **(1) a severity chip** ("HIGH"/"MEDIUM"), **(2) a status** ("Scanning"/"Queued"), **(3) the flagged quote itself** in quotation marks, **(4) a named risk-type label** ("Forward-Looking Statement," "Unsupported Claim," "Off-Voice Superlatives," "PCI Data Exposure"), **(5) a one-line "why"** citing the specific rule or internal source ("Return guarantees without disclaimers violate FINRA 2210 communication rules"; "Internal docs support integration with 42 CRM platforms, not 500"), and **(6) a suggested one-click remediation** ("Add required disclosure," "Auto-Correct to 42," "Rewrite in approved voice," "Mask as ****-****-****-1734") [fact, luthor.ai homepage]. Policy categories run as parallel lanes with live status (Performance/Guarantees/Disclosures/Projections/Testimonials/Fees/Citations/PII), each independently "Scanning"/"Queued" — i.e., the UI visibly shows *what checks are still running or pending*, which is a partial answer to "what was NOT yet checked" (in-flight, not absent-by-design). [fact] Findings explicitly distinguish **regulatory violations** (FTC/FINRA/UDAAP/GDPR) from **unsupported factual claims** (checked against "Product Specs, Pricing Data, Historical Claims, Support Docs") from **brand-voice** issues from **PII/PCI leakage** — four distinct policy domains in one engine.

**(b) Workflow & roles** — [inference from marketing copy, not documented workflow] Positioned as continuous/automatic first-pass review ("Automatically review every asset... before publication") rather than a human-in-the-loop queue UI; the audit trail panel emphasizes **outcome metrics** ("Quarterly Impact $2.4M," "340% Fines Avoided YoY," "Hours Saved 14,200," "Issues Caught 287," "Detection Rate 98.4%," "Time to Fix 6 Min," "Risk Reduced 94%") rather than describing an approval workflow — this reads as an ROI dashboard for compliance leadership, not an operational review queue [fact, homepage "Audit Trail" section]. No public detail on maker-checker roles, escalation, or exception recording was found.

**(c) Information architecture** — [inference] Primary object appears to be the **content asset** (text/image/video/audio/SMS/social/URL), ingested and scanned continuously; the "Policy Engine" and "Audit Trail" are dashboard-level views across all assets, not per-asset drill-downs (at least not shown on the marketing site).

**(d) API design** — no public API reference found; site emphasizes "integrate Luthor in days, not months" without technical detail [fact, homepage CTA]. No webhook/idempotency documentation discoverable in this pass.

**(e) Packaging & pricing** — [fact] No public pricing; enterprise/demo-gated ("Get a demo"). Enterprise trust badges shown: SOC2 Type II, AES-256 encryption, **Zero Data Retention**, Audit Logs [fact, homepage "Engineered for the enterprise" section] — Zero Data Retention as a headline trust signal is notable for content compliance tooling handling sensitive campaign drafts.

**(f) Steal / avoid** — **Steal:** the finding-card anatomy (quote → severity → named risk type → one-line cited reason → one-click fix) is close to gold-standard and directly portable to our design; also steal "Zero Data Retention" as an explicit trust badge for lender procurement conversations. **Avoid:** leading with ROI/marketing metrics ("$2.4M impact," "94% risk reduced") in the *product* audit trail rather than operational facts blurs the line between a sales dashboard and an evidentiary record — our sealed evidence record must never look like a marketing scoreboard; it must look boring, dated, and complete.

## 4. Litmus

**Sources:** [Litmus 101: previews & pre-send checks](https://www.litmus.com/blog/litmus-101-a-how-to-on-previews-pre-send-checks), [Litmus Checklist](https://www.litmus.com/email-checklist/), [Litmus Spam Testing](https://www.litmus.com/spam-filter-tests), [Litmus accessibility checks announcement](https://www.litmus.com/blog/accessible-email-made-easy-introducing-accessibility-checks-in-litmus), [Litmus pricing via Vendr](https://www.vendr.com/marketplace/litmus)

**(a) Check result presentation** — [fact] The **Checklist** pattern is literally a scorecard: dozens of discrete, independently pass/fail checks grouped by category — Code & HTML, Accessibility (40+ checks, screen-reader and structure focused), Images, Links/UTMs, Spam/Deliverability [fact, litmus.com/email-checklist, accessibility blog post]. **Spam Testing** separately runs the email against 25+ spam filters and returns a **deliverability score** plus categorized flags: authentication (SPF/DKIM/DMARC), blocklist status, content triggers, reputation concerns [fact, litmus.com/spam-filter-tests]. This is the cleanest example of a **checklist/scorecard UX** in the set: many small, independently-labeled pass/fail items rolled into a single glanceable list, rather than one holistic risk score.

**(b) Workflow & roles** — [inference] Litmus is fundamentally a pre-send QA tool, not an approval/governance tool — no maker-checker or sign-off workflow was found in public docs; it's positioned as something a single email builder runs before handing off to their ESP.

**(c) Information architecture** — [inference] Primary object is the **individual email/campaign build**; "previews" and "checks" are actions performed against that one object, surfaced together in one pre-send screen ("Litmus 101" 3-step flow: preview → pre-send checks → send).

**(d) API design** — [fact] A documented public API exists (docs.litmus.com), including an [Accessibility API endpoint](https://docs.litmus.com/v3/accessibility) — confirms Litmus exposes checks (not just previews) as callable API resources, relevant precedent for our own "invoke a check" API shape.

**(e) Packaging & pricing** — [fact] Sales-gated tiers as of Aug 2025: **Core** ~$500/mo (5 full users, 2,000 previews/mo, 500k analytics opens/mo, 50k Personalize impressions/mo), plus higher **Custom** tiers for collaboration/personalization vs. deliverability insights, and an **Enterprise** tier (unlimited seats/usage, QA on 100+ clients/devices) [fact, Vendr/xpay/PricingSaaS secondary sources — pricing pages themselves are sales-gated, so treat exact numbers as [inference]-adjacent, sourced from third-party pricing trackers, not Litmus's own site]. Packaging axis is **usage volume (previews, opens) × seats**, not per-check.

**(f) Steal / avoid** — **Steal:** the checklist/scorecard pattern itself — a long list of small, independently labeled, category-grouped pass/fail checks is exactly the right IA for "what did we check and what's the status of each," and should be the literal layout of our per-send compliance panel (grouped by Consent / Audience Quality / Content / Identity, each item pass/fail/warn). **Avoid:** Litmus's checklist has no visible "why does this rule exist / what regulation" — it's a UX/quality checklist, not a compliance-with-citation checklist; if we copy the layout we must still add Luthor/Saifr-style citations per item, which Litmus itself lacks.

## 5. Fyno (India)

**Sources:** [Fyno DPDP consent platform comparison blog](https://www.fyno.io/blog/dpdp-consent-platform-enforcement-comparison), [Fyno homepage](https://fyno.io/), [Fyno idempotent requests blog](https://www.fyno.io/blog/idempotent-requests-in-notification-infrastructure-cm4s7axck002x9jffvml6fx1y), [Fyno idempotency docs](https://fyno.io/docs/idempotent-requests), [Fyno webhook workflow docs](https://docs.fyno.io/docs/workflow-webhook-trigger)

**(a) Check result presentation / positioning** — [fact] Fyno's core positioning claim, stated explicitly, is the **governance vs. enforcement** distinction: "RegTech platforms capture, store, and manage user consent but don't connect to your SMS gateways, WhatsApp Business API, or email systems. Communication orchestration sits between RegTech and CPaaS vendors, querying consent status before every promotional send and blocking non-compliant messages." [fact, fyno.io/blog/dpdp-consent-platform-enforcement-comparison] This is directly relevant to our own pipeline framing: **consent governance (capture/store) is a different system from consent enforcement (check-at-send)**, and Fyno's entire pitch is being the enforcement layer that sits in front of the send. [fact] Enforcement checks are described as: consent status, DLT (India telecom Distributed Ledger Technology registration) rules, and DND (Do Not Disturb registry) — validated "on channel, topic, and DND" at send time.

**(b) Workflow & roles** — [inference] No public maker-checker or human-review workflow found; Fyno is positioned as a fully automated, machine-speed gate (block/allow), not a human-reviewed queue — consistent with its "vendor-agnostic middleware" role rather than a compliance-officer-facing product.

**(c) Information architecture** — [inference] Primary object is the **message/send event** flowing through an orchestration pipeline; consent, DLT, DND are attributes checked against that event, not separate top-level objects a human browses.

**(d) API design** — [fact] Fyno documents **idempotency keys** explicitly as a first-class API concept, but scoped narrowly: "Fyno supports idempotency with only 3 APIs — Event, Event Bulk, and Automations APIs" [fact, fyno.io/docs/idempotent-requests] — i.e., idempotency is not blanket-applied to the whole API surface, only to the send/trigger-shaped endpoints, which is a pragmatic, worth-copying scoping decision (idempotency matters most where retries could cause duplicate sends/actions, less on read endpoints). [fact] Webhooks are a core primitive — "How to create a workflow using Webhook" is a top-level docs page, meaning webhook-triggered workflows (not just webhook notifications-out) are part of the product model [fyno.io docs].

**(e) Packaging & pricing** — no public pricing found; vendor-agnostic integration model (works alongside OneTrust, Leegality, IDfy Privy) rather than owning the consent record itself [fact, fyno.io/blog].

**(f) Steal / avoid** — **Steal:** the sharp, explicit **governance vs. enforcement** vocabulary — we should use exactly this language internally and possibly externally: "does the rule check happen at send-time, against live state, and can it actually block the send" vs. "is there merely a record of consent somewhere." Also steal the narrow idempotency scoping (apply idempotency keys only to send/trigger endpoints, not universally). **Avoid:** Fyno's public materials show no evidence-record/audit-trail UI for a human reviewer — it's a pure machine gate; if we only build the Fyno-style enforcement gate without Veeva/Saifr-style human-legible evidence, we'll satisfy real-time blocking but fail the "why did we decide X" audit requirement regulators/lenders will ask for.

## 6. CarmaOne and Exotel (collections calling-window/script enforcement)

**Sources:** [Exotel: RBI-Compliant AI Call Flow for Debt Collections](https://exotel.com/blog/rbi-compliant-ai-collections/), [CarmaOne: RBI Compliant AI Collections guide](https://www.carmaone.ai/blog/rbi-compliant-ai-collections-guide-india-2026)

**(a) Check result presentation** — [fact] Both vendors describe a **compliance dashboard** (not per-message findings) aggregating operational metrics: calling-hour adherence, contact-frequency compliance, disclosure completion rates, DND-scrubbing results, consent status (CarmaOne); DND scrub timestamps, calling-hour suppressions, adherence scores per campaign, escalation rates, recording completeness (Exotel) [fact, both blog posts — note these are vendor blog/marketing content, not product documentation, so treat specifics as [inference]-leaning]. The enforcement model is **hard, not advisory**: "Compliance officers get a dedicated dashboard... calls blocked outside hours rather than merely scheduled within hours" and "hard-coded outbound calling window restrictions (strictly forbidding calls prior to 8 AM or past 7 PM)" [fact, CarmaOne blog]. This is the calling-domain equivalent of our own pre-send gate: the system refuses to let the disallowed action happen at all, rather than just flagging it after the fact.

**(b) Workflow & roles** — [inference] "Un-editable cross-channel audit trails" are named as a requirement/feature [CarmaOne blog] — i.e., audit-trail immutability is treated as a compliance necessity in Indian lending/collections, directly validating our own "seal an immutable evidence record" design goal. No detail found on human review/override workflow (fix / accept-with-reason / abandon equivalent) — these products appear to be prevention-first (block outright) rather than review-and-decide.

**(c) Information architecture** — [inference] Primary object appears to be the **campaign/agent's call queue**, with compliance metrics rolled up at the campaign and supervisor level (a "single supervisor view" per Exotel) rather than a per-call finding UI.

**(d) API design / (e) Packaging** — no public API or pricing detail surfaced for the compliance-specific features in this pass.

**(f) Steal / avoid** — **Steal:** "blocked, not merely scheduled" — i.e., hard technical enforcement of the rule at the point of action, and the explicit framing of the audit trail as **un-editable**, which we should state as a design requirement, not just an implementation detail. **Avoid:** rolling everything into an aggregate supervisor dashboard (adherence scores, percentages) risks hiding the *specific* case-level "why was this blocked" reasoning that a regulator or reviewer will ask for on any individual campaign — aggregate dashboards are good for oversight, bad as the sole audit artifact.

## 7. Braze

**Sources:** [Rate limiting and frequency capping docs](https://www.braze.com/docs/user_guide/engagement_tools/campaigns/building_campaigns/rate-limiting/), [Frequency capping FAQ](https://www.braze.com/docs/user_guide/messaging/messaging_fundamentals/frequency_capping/faq), [Approvals for campaigns and Canvases](https://www.braze.com/docs/user_guide/messaging/governance/approvals), [Messaging Rules – Approvals](https://www.braze.com/docs/user_guide/messaging/governance/approvals/messaging_rules), [Intelligent Timing](https://www.braze.com/docs/user_guide/brazeai/intelligence_suite/intelligent_timing), [Frequency capping explainer](https://www.braze.com/resources/articles/whats-frequency-capping)

**(a) Check result presentation** — [fact] Frequency capping is a **rule-based, per-user gate**: "limits how many messages any one customer can receive within a set time period, applying across campaigns and channels simultaneously," counted **per dispatch** (each send counts once regardless of variant) [fact, Braze docs]. Rate limiting is a separate, distinct control capping **messages per minute during a single send** (infrastructure/throughput protection, not user-experience protection) — this is a useful conceptual split we should keep distinct in our own design (audience-quality throttling vs. infrastructure throttling are different concerns even though both look like "rate limits"). [fact] Certain campaign types (transactional, API campaigns via `override_frequency_capping: true`) can explicitly **bypass** the cap — i.e., Braze's model has a built-in, named "exception" flag at the API level, not just a UI override.

**(b) Workflow & roles** — [fact] **Approvals** add "a final checkpoint... before launch," requiring sign-off on each of four sections independently: **Messages, Delivery, Target Audience, Conversion Events** — a reviewer must approve each section, not just the campaign as a whole [fact, braze.com/docs/.../approvals]. **Messaging Rules** extend this: you can require an *additional* approval step once a campaign's reachable audience exceeds a threshold — i.e., approval requirements can scale with blast radius, a good pattern for risk-proportionate review. [fact] Approval workflow is **off by default** and must be turned on in Settings, with explicit permissioning for who can approve/deny. [fact] Important limitation: **"Campaign approval is not supported for API campaigns and Transactional Email campaigns"** — a real gap between the governed UI path and the programmatic path that we should explicitly avoid replicating (our pipeline must gate campaigns regardless of entry point).

**(c) Information architecture** — [inference] Primary object is the **Campaign or Canvas** (Canvas = multi-step journey); approvals and frequency capping are properties/gates attached to that object, reviewed section-by-section in a single summary screen before launch.

**(d) API design** — [fact] `override_frequency_capping` is a literal request-body boolean on the send API — an explicit, auditable, named escape hatch rather than a silent bypass. [inference] This is a genuinely good API-design pattern for our own "accept-with-reason" exception: an exception should be a named, typed field in the API payload (not an implicit state), so every send request self-documents whether an override was invoked.

**(e) Packaging & pricing** — [fact] Custom quote only; three named tiers **Core / Pro / Enterprise**, priced on MAU + message volume + channel mix + contract length, no public price list [fact, multiple secondary trackers, Braze's own pricing article is directional/marketing not a price sheet]. Approvals and Messaging Rules are governance features gated to non-Core tiers per typical enterprise-tier gating [inference — not explicitly confirmed which tier gates approvals].

**(f) Steal / avoid** — **Steal:** (1) per-*section* approval (Messages/Delivery/Audience/Conversion each independently signed off) rather than one global approve button — maps well onto our own "audience+message+identity+rules" pipeline stages; (2) audience-size-triggered additional approval (Messaging Rules) as a risk-proportionate escalation pattern; (3) the named, typed override flag in the API request body as the shape for "accept-with-reason." **Avoid:** the approval workflow silently not applying to API/transactional sends — any campaign-operations pipeline we build must make the gate un-bypassable by choice of integration path, or it isn't a real control.

## 8. CleverTap

**Sources:** [Audit Logs docs](https://docs.clevertap.com/docs/audit-logs), [Automated Audit Log Exports for SIEM](https://docs.clevertap.com/docs/automated-audit-log-exports-for-siem), [Campaign Approval Workflow docs](https://docs.clevertap.com/docs/campaign-approval-workflow), [CleverTap pricing](https://clevertap.com/pricing/)

**(a) Check result presentation** — [inference] CleverTap's approval workflow is a binary gate (approve/reject) reviewed against "segment, time, and campaign copy" — no severity vocabulary or structured findings; it is a manual human review, not an automated check-and-flag system [fact, docs.clevertap.com/docs/campaign-approval-workflow].

**(b) Workflow & roles** — [fact] Clean, well-specified **maker-checker** model: a new system role **Approver** is introduced; a **Creator** cannot publish until an Approver signs off; **Admins are Approvers by default**; custom roles can be scoped to approver-only access [fact, docs page]. Concrete state-machine behaviors, explicitly documented — genuinely good spec-writing worth emulating verbatim in our own PRD:
  - Rejected campaigns notify the creator by email; **rejection comments are delivered via that email**, not a persistent in-app comment thread [fact] — this is actually a **weak** pattern (see Avoid below).
  - If a campaign's scheduled send time arrives before approval, it is **marked Expired**, not silently sent or silently held — the creator must **clone and reschedule**, they cannot "un-expire" [fact].
  - **Recurring campaigns**: after a content edit, the campaign automatically reverts to "Pending approval" for the next run, even after prior runs were approved — i.e., approval is tied to *content version*, not to the campaign object permanently [fact].
  - Turning approval **off** while items are pending **auto-approves them** — a documented, explicit (if slightly alarming) edge-case behavior [fact].
  - Creators **can edit and resend** a rejected campaign for approval — rejection is not terminal.
**(c) Information architecture** — [inference] Primary object is the **Campaign**; approval status is a property/state of the campaign object, and reachability/segment-quality info is shown as a related panel ("Segments > reachability breakdown by channel with reasons: Token Not Present, User Unsubscribe, Token Not Generated, App Uninstall") [fact] — notably, this reachability breakdown *is* an audience-quality "why some recipients will be excluded" explanation, relevant to our "audience quality" check category.

**(d) API design** — [fact] Audit logs can be **auto-exported every 24 hours to S3/GCS/Azure Blob** for SIEM integration and long-term retention/compliance [fact, docs.clevertap.com/docs/automated-audit-log-exports-for-siem] — i.e., CleverTap treats the audit log as an externally-owned compliance artifact by design, pushing it out of the product rather than assuming customers will only ever view it in-app.

**(e) Packaging & pricing** — [fact] Tiered by **MAU** (Essentials from $75/mo for 5,000 MAU; Advanced; Premium), with overage pricing (~$1.50 per additional 100 MAUs) [fact, softwarefinder/clevertap.com/pricing via secondary aggregator — treat exact numbers as approximate]. Maker-checker/approval appears to be a **security-tier feature** gated in Settings > Security, not obviously tied to a specific paid plan in the docs found.

**(f) Steal / avoid** — **Steal:** (1) the fully-specified state machine for approval/expiry/re-approval-on-edit is an excellent template to copy directly for our own decision states; (2) auto-exporting audit logs to customer-owned cloud storage on a schedule, so the evidence record isn't trapped in our app; (3) surfacing audience-quality exclusion *reasons* (token missing, unsubscribed, uninstalled) as a named breakdown, not just a raw reachability number. **Avoid:** delivering rejection reasoning only via email rather than a persistent, structured in-app comment/audit-trail entry — this breaks the "immutable evidence record" requirement (email is not part of the sealed record) and should not be our pattern; rejection comments must live in the system of record.

## 9. Credgenics

## 11. Evidence-record / audit-certificate design patterns (cross-domain)

**Sources:** [DocuSign: What Is an Audit Trail?](https://www.docusign.com/blog/what-is-an-audit-trail), [DocuSign trust/transaction data](https://www.docusign.com/trust/security/transaction-data-use), [Docusign-Issued Digital Certificates for Docusign Notary](https://www.docusign.com/blog/docusign-issued-digital-certificates-docusign-notary), [Vanta Trust Center product page](https://www.vanta.com/products/trust-center), [Vanta Trust Center help docs](https://help.vanta.com/en/articles/11345469-vanta-trust-center), [general tamper-evidence/hashing sources synthesized]

1. **DocuSign Certificate of Completion** — [fact] Every signed envelope gets a standalone **Certificate of Completion**: who signed, precise timestamps, IP addresses/device/location, authentication method, bundled with the final document itself, and the whole package is **digitally sealed with PKI** so any post-hoc alteration is cryptographically detectable [fact, docusign.com/blog/what-is-an-audit-trail; docusign.com/trust/security/transaction-data-use]. **What makes it feel trustworthy:** (i) it is a *separate, self-contained artifact* from the transaction itself — you can hand the certificate alone to a third party (a court, an auditor) without giving them access to your live system; (ii) it names the exact fields a skeptic would ask for (who/when/where/how-authenticated) rather than a vague "verified" badge; (iii) tamper-evidence is structural (PKI seal) not just a claim in the UI copy.

2. **OneTrust's "receipt" + point-in-time snapshot** (see Section 10) — [fact/inference] What makes a consent receipt feel trustworthy is that it's reconstructable independent of current system state — it shows the banner/policy *as it was*, not as it is now.

3. **Vanta Trust Center** — [fact] Rather than a one-time PDF, Vanta's public Trust Center shows **continuous, real-time evidence of active controls** ("goes beyond a one-time compliance snapshot") plus visit/access-request analytics for the trust page itself [fact, vanta.com/products/trust-center; help.vanta.com]. **What makes it feel trustworthy:** it is *live and dated*, not a static claim — the viewer can see the control is passing *right now*, with a visible last-checked timestamp, which is a fundamentally different trust signal than a certificate frozen at issuance. [inference] This "live continuous" pattern and DocuSign's "frozen, sealed, portable" pattern are **complementary, not competing** — our own product likely needs *both*: (a) a live dashboard showing current rule/check status, and (b) a frozen, portable, sealed evidence certificate per campaign decision that never changes after the fact.

4. [inference, synthesized from general tamper-evidence sources] The common technical backbone across trustworthy audit artifacts is a **cryptographic hash + timestamp anchor**: "a document is tamper-proof in practice when any change to it is detectable" — the design lesson is not that we must prevent editing, but that we must make any post-seal edit **provably detectable** (e.g., hash the sealed record content at seal-time, display/export that hash alongside the record).

**Steal for our evidence record:** (1) make the sealed record a portable, standalone artifact (PDF/JSON bundle) independent of live app state — reviewers, lenders, and regulators should be able to hold it without needing access to our system; (2) name the specific fields a skeptic wants (who decided, what rule version, what was flagged, what evidence/citation, what override reason, timestamp, hash) rather than a vague "approved ✓"; (3) include a visible integrity hash/fingerprint on every exported certificate, computed at seal time.

## PATTERNS TO ADOPT

1. **Four-part finding anatomy — flag, cite, explain, fix** (Saifr, Luthor): every check finding should show the exact flagged text/data, the specific rule/policy it violates (with citation), a one-line plain-language "why," and a suggested remediation or required disclosure.
2. **Checklist/scorecard layout for the pre-send panel** (Litmus): group findings into named categories (Consent / Audience Quality / Content Compliance / Identity Resolution), each a short list of independently pass/fail/warn items, not one holistic score.
3. **Claim-to-source citation as a first-class, reusable object** (Veeva PromoMats Claims Library): every factual/compliance claim should link to the specific policy or reference document + anchor that justified it, auto-maintained if the source updates.
4. **Section-by-section approval, not one global "Approve" button** (Braze): require independent sign-off on Audience, Message, Rules/Compliance, and Delivery Timing sections of a campaign before send.
5. **Risk-proportionate escalation by blast radius** (Braze Messaging Rules): require an additional approval step once a campaign's reachable audience crosses a threshold.
6. **Named, typed override field in the API request, not a silent bypass** (Braze's `override_frequency_capping`): "accept-with-reason" should be a required, structured field on the send request, always logged.
7. **Fully specified approval state machine, including expiry-on-timeout and re-approval-on-edit** (CleverTap): document (and build) explicit states for pending/approved/rejected/expired/re-submitted, including what happens if a scheduled send time arrives before sign-off.
8. **Governance vs. enforcement as distinct, explicitly named layers** (Fyno): consent/rule *storage* is a different system responsibility than send-time *enforcement*; our product should be unambiguous about which one it is and check live state at send time, not just at authoring time.
9. **Hard technical blocking, not advisory flagging, for calling-window/consent violations** (CarmaOne/Exotel): where a rule is unconditional (e.g., DND, banned hours), the system should refuse the action outright rather than merely warn.
10. **Portable, self-contained, hash-sealed evidence certificate, separate from the live audit-log dashboard** (DocuSign + Vanta combined): ship both a live "current status" view and a frozen, exportable, tamper-evident certificate per decision that can be handed to a regulator without system access.
11. **Point-in-time snapshot of the exact policy/message version evaluated** (OneTrust): the sealed record must capture what rule version and what exact message content were checked, not just a boolean outcome, so it remains interpretable after rules change.
12. **Externalize the audit log on a schedule, don't trap it in-app** (CleverTap SIEM export): auto-export sealed records to customer-controlled storage (S3/GCS/Blob) so the evidence record survives independent of our platform's availability.

## ANTI-PATTERNS TO AVOID

1. **Asserting compliance/audit-trail quality as a marketing claim without ever showing the artifact** (Credgenics): our evidence record must be concretely demoable and inspectable, not a bullet point on a homepage.
2. **Governance gates that don't apply uniformly across entry points** (Braze: approvals skip API and transactional campaigns): any rule engine we build must gate every path into a send (UI, API, scheduled, retry) — a control that can be routed around isn't a control.
3. **Delivering rejection/exception reasoning through a side channel (email) instead of the system of record** (CleverTap): all decision reasoning — approve, reject, accept-with-reason — must be written into the persistent, sealed evidence trail itself, not left in an email inbox.
4. **Leading the audit trail with ROI/marketing metrics instead of operational facts** (Luthor's "$2.4M impact," "94% risk reduced" inside its "Audit Trail" panel): a sealed evidence record must read as boring, dated, and complete — outcome/ROI dashboards belong in a separate reporting view, never mixed into the artifact meant to satisfy a regulator or auditor.
